# 回归验证流程（Regression Check）

代码生成完成后，**必须执行**以下回归验证流程，确保还原度达标。此流程为强制步骤，不可跳过。

> **与检查点系统的集成**：本文件对应 `CP-11 RegressionReport`。必须在 CP-10（代码输出）和 CP-10.5（背景图验证）完成后才能开始。验证报告是 CP-11 的产物，必须使用 `──── CP-11 RegressionReport ────` 格式输出。

---

## 一、验证时机

回归验证在以下时机触发：

1. **新建流程**（`create-workflow.md`）的 Step 10 之后
2. **变更流程**（`update-workflow.md`）的 Step 5 之后
3. 用户手动要求 "检查还原度" / "验证代码" 时

---

## 二、验证流程

### Step 1：获取设计稿基准数据

重新调用 `get_figma_data` 获取设计稿节点树，作为验证基准：

```
get_figma_data({
  fileKey: "<fileKey>",
  nodeId: "<nodeId>"
})
```

**注意**：此次获取用于验证，需与生成代码时使用的参数完全一致。

### Step 2：逐维度比对

对生成的代码逐维度与设计稿数据进行比对，生成**定量验证报告**。

#### 2.8 视觉截图对比（强制步骤）

在数据维度验证之外，**必须执行**视觉截图对比。此步骤为强制步骤，不可跳过。

**升级理由**：纯数据维度验证无法发现以下问题：
- 背景图缺失（数据中有 IMAGE fill 但代码未实际渲染）
- 同行元素被换行（布局属性正确但嵌套层级丢失）
- 图片被裁剪/截断（文件存在但内容不完整）
- 多层 fill 遗漏（SOLID 和 GRADIENT 正确但 IMAGE 层缺失）

**执行流程：**

```
1. 启动本地开发服务器
   → npm run dev / pnpm dev

2. 使用 Playwright 对生成的页面截图
   → 等待页面加载完成（networkidle）
   → 全页面截图保存为 .vrt/actual-{timestamp}.png

3. 调用 download_figma_images 获取设计稿的 PNG 导出
   → 使用根节点 ID
   → pngScale: 2（2x 高清）
   → 保存为 .vrt/expected-{timestamp}.png

4. 运行像素级对比
   → 使用 scripts/vrt-check.cjs 或 pixelmatch 库
   → 生成差异图 .vrt/diff-{timestamp}.png

5. 执行分区域对比（见下方）

6. 输出对比结果
```

##### 2.8.1 分区域截图对比（强制步骤）

**整体截图对比容易掩盖局部偏差**（如 Banner 背景缺失但整体差异率仍在阈值内），因此必须将页面划分为多个区域逐区对比：

**区域划分规则：**

按 Figma 节点树的第一层子节点（通常对应页面的主要区块）自动划分区域：

| 区域类型 | 典型节点 | 重点检查内容 |
|---------|---------|-------------|
| Banner/Hero | 顶部大图区域 | 背景图完整性、文字叠加层、按钮位置 |
| 导航/标题栏 | Header/NavBar | 元素对齐、图标完整 |
| 内容简介区 | 文字+图标区域 | 图文排列方向、同行元素包裹 |
| 列表/卡片区 | 重复元素区域 | 卡片间距、图片尺寸、文字截断 |
| 底部/Footer | 底部区域 | 定位方式、间距 |

**分区对比流程：**

```
对每个区域：
1. 在设计稿截图中裁切出该区域（按节点坐标）
2. 在实际页面截图中裁切出对应区域
3. 逐区进行像素级对比
4. 单独计算每个区域的差异率
```

**分区对比结果输出：**

```
📸 分区域视觉对比结果：
```

**判定标准：**

| 差异率 | 判定 | 处理 |
|--------|------|------|

- 视觉对比**纳入综合评分**，权重为 0.05（从其他维度均摊扣除）

- 如本地开发环境不可用（无法启动 dev server），降级为"数据维度验证 + 背景图专项验证"，在报告中标注"视觉截图对比已降级"

### Step 4：自动修复不通过项

**当验证报告中存在不通过项时，自动执行修复：**

1. **间距/颜色/字体问题** → 直接使用 `replace_in_file` 修改对应的 className
2. **图片缺失** → 重新调用 `download_figma_images`
3. **组件映射错误** → 替换为正确的组件
4. **交互逻辑缺失** → 补充 hover 样式、click 处理器等
5. **代码质量问题** → 修复 import、拆分超长文件
6. **Manifest / 幂等性问题** → 补齐缺失字段、修正命名与排序规则后重新验证
7. **同行元素布局丢失** → 在代码中补充缺失的 `flex flex-row` 包裹容器，确保同行元素不换行
8. **Auto Layout 嵌套被扁平化** → 恢复 Figma 中嵌套的 flex 容器层级，避免合并
9. **背景图缺失/遗漏** → 检查 fills 数组中的 IMAGE 类型，使用节点渲染模式（模式 C）重新下载，并以 CSS `background-image` 方式设置
10. **背景图被裁剪/截断** → 检查 `clipContent` 和 `cropTransform`，改用模式 C 或请求用户提供手动导出的原图
11. **页面根容器固定宽度** → 将 `w-[1920px]` 改为 `w-full min-h-screen`
12. **内容区未居中** → 将 `ml-[Npx]` 改为 `max-w-[Npx] mx-auto w-full px-4`
13. **子元素固定宽度溢出** → 将内容区子元素的 `w-[Npx]` 改为 `w-full`
14. **超宽背景固定偏移** → 将固定 `margin-left` 改为 `overflow-hidden` + `object-cover`
15. **坐标未被使用导致布局偏移** → 重新基于坐标数据分析布局关系，修正 flex 方向和间距
16. **布局补丁式修复循环** → 触发止损：停止补丁修复，回退到坐标系统建立步骤，推翻重写该区域

**修复后重新执行 Step 2-3**，直到所有硬性不通过项清零，或综合得分 ≥ 90%。

```
修复循环上限：最多 2 轮自动修复
  第 1 轮：修复所有 FAIL 项
  第 2 轮：如果还有 FAIL 项，再修复一次
  超过 2 轮仍有 FAIL → 输出剩余问题，标记为需人工处理
```

## 五、边界情况处理

### 5.1 设计稿数据不完整

如果 `get_figma_data` 返回的节点树被截断（常见于大型页面），验证时：
- 只验证已获取到的节点
- 在报告中标注 "部分验证" 和已验证节点数/总节点数

### 5.2 动态内容

设计稿中的文本内容可能与 mock 数据不完全一致（如设计师使用占位文本），文本内容比对时：
- 只验证**文本存在性**（节点有文本），不验证具体文案
- 数值格式需一致（如 "1,280人" 的千位分隔符）

### 5.3 响应式

如果设计稿只有单一宽度画板，验证自适应布局时：
- **强制验证**：即使只有单一宽度画板，仍然必须验证页面在 1280px 和 1024px 视口下无水平溢出
- 不要求在小屏下完美还原（因为没有小屏设计稿）
- 只验证「不溢出、不留白、可阅读」的最低保障
```
ℹ️ 设计稿为固定宽度 ({width}px)
  - ✅ 自适应输出已启用：max-width 约束 + 居中 + 弹性子元素
  - ✅ 1280px 视口验证通过：无水平溢出
  - ✅ 1024px 视口验证通过：内容可阅读
  - ℹ️ 未验证完整响应式适配（无小屏设计稿）
```
