# 设计稿质量预检（Design Quality Precheck）

在代码生成前，**必须先执行**设计稿质量预检，识别不规范的设计结构和复合视觉效果节点，制定针对性的处理策略。此步骤可有效避免后续反复调试 CSS 渐变、层叠效果等，减少沟通成本。

> **与检查点系统的集成**：本文件对应 `CP-2.5 PrecheckReport`。必须在 CP-2（获取设计数据）完成后才能开始。预检报告是 CP-2.5 的产物，**必须使用第三节的完整格式输出**，缺少任何一个区块都视为门禁不通过。

---

## 一、预检时机

在 `create-workflow.md` 的 Step 2（获取设计数据）完成后、Step 3（输出结构摘要）之前执行。

---

## 二、预检项目

### 2.1 复合视觉效果节点识别（关键项）

**此项是减少还原试错的核心规则。**

#### 判定条件（满足任意一条即判定为"复合视觉效果节点"）

| 编号 | 条件 | 说明 | 处理策略 |
|------|------|------|---------|
| C1 | 单节点 fills 数组包含 **IMAGE + GRADIENT_LINEAR/RADIAL** 混合（≥ 2 种类型） | 图片和渐变叠加，CSS 无法精确复现混合效果 | **整体导出为图片** |
| C2 | fills 中 IMAGE 类型包含 **`cropTransform`** 字段 | Figma 私有的裁剪变换矩阵，CSS `object-fit/position` 无法精确还原 | **整体导出为图片** |
| C3 | 单节点 fills 数组长度 **≥ 3**，且包含至少 1 个 IMAGE 和至少 1 个 GRADIENT | 三层以上叠加效果，CSS 多背景层叠结果可能与 Figma 渲染不一致 | **整体导出为图片** |
| C4 | 节点 type 为 GROUP 且子节点中包含多个渐变 RECTANGLE 相互叠加（坐标重叠面积 > 80%） | 多个渐变矩形叠加模拟复合效果 | **整体导出为图片** |
| C5 | 节点包含 `blendMode` 且值不是 `PASS_THROUGH` 或 `NORMAL` | 非标准混合模式，CSS `mix-blend-mode` 渲染结果可能有差异 | **整体导出为图片** |
| C6 | 渐变角度为非标准角度（非 0°/45°/90°/135°/180°/225°/270°/315°），且渐变色标 ≥ 3 个 | 复杂斜角渐变，Figma 渐变坐标系与 CSS 不完全一致 | **优先导出为图片**，简单渐变可尝试 CSS |
| C7 | 节点 fills 包含 IMAGE 类型，且同时包含 SOLID 或 GRADIENT 类型（≥ 2 层 fill） | 多层填充叠加效果（如底色+背景图+渐变遮罩+半透明层），CSS 多背景语法无法精确还原 Figma 的叠加渲染顺序和混合效果 | **整体导出为图片**（使用 MCP 节点渲染模式，不传 imageRef） |
| C8 | 节点 `clipContent === true` 且包含 IMAGE fill，且 IMAGE fill 存在 `cropTransform` | clipContent 导致 MCP 节点渲染按边界裁切，cropTransform 导致素材被错误裁剪 | **整体导出为图片**，导出后必须验证视觉完整性（见 `image-workflow.md` 第八节） |

#### 处理策略：整体导出为图片

当节点被判定为复合视觉效果节点时：

1. 使用 `download_figma_images` 直接导出该**节点整体**为 PNG（`pngScale: 2`）
2. 在代码中用 `<img>` 或 CSS `background-image` 引用导出的图片
3. **禁止**尝试用 CSS 渐变、多层背景去模拟复合效果
4. 如果该节点同时承担交互功能（如可点击区域），则图片作为背景层，交互元素独立叠加

```tsx
// ✅ 正确：复合视觉效果直接用导出图片
<div className="relative w-full h-[420px]">
  <img
    src={bgComposite}
    alt=""
    aria-hidden="true"
    className="absolute inset-0 w-full h-full rounded-lg"
    style={{ objectFit: 'fill' }}
  />
  {/* 交互内容叠加在图片上方 */}
  <div className="relative z-10">
    {/* ... */}
  </div>
</div>

// ❌ 错误：用 CSS 多层渐变模拟复合效果
<div style={{
  background: 'linear-gradient(88deg, ...), linear-gradient(93deg, ...), url(decor.png)',
  backgroundSize: 'cover',
}}>
```

#### 特殊情况：可用 CSS 还原的简单渐变

以下情况**不**判定为复合视觉效果节点，可以用 CSS 还原：

1. 单个 `GRADIENT_LINEAR` 且角度为标准角度（0°/90°/180°/270°），色标 ≤ 3 个
2. 单个纯色填充 `SOLID`
3. 单个 IMAGE 填充且无 `cropTransform`
4. 渐变终止色与相邻区域颜色同色系（HSL 色相差 ≤ 10°）

### 2.2 设计稿结构规范性检查

遍历节点树，检查以下不规范结构：

| 检查项 | 检测方法 | 不规范影响 | 处理建议 |
|--------|---------|-----------|---------|
| GROUP 替代 FRAME | 节点 `type === 'GROUP'` 且有多个子节点 | 丢失 Auto Layout 语义，只能绝对定位 | 标注为 `⚠️ 手动布局`，代码中用 flex/grid 推导布局 |
| 无 Auto Layout | FRAME 节点 `layoutMode` 为空 | 子元素缺少 flex 信息，需手动推导 | 按 `create-workflow.md` Step 7 坐标推导布局 |
| 渐变终止色与相邻区域色温不一致 | 渐变最后一个色标的 RGB 与相邻节点背景色的 HSL 色相差 > 30° | 过渡区域出现色带 | 在代码中修正终止色为相邻区域同色系 |
| 重复节点名称 | 同一层级多个子节点 `name` 完全相同 | 代码生成时可能命名冲突 | 自动追加序号后缀 |
| 超大节点树 | 单个节点子孙数量 > 100 | MCP 返回数据可能被截断 | 分批获取，增加 depth 参数 |

### 2.3 数据完整性检查

| 检查项 | 检测方法 | 处理 |
|--------|---------|------|
| 节点树被截断 | 叶子节点中存在 `type` 为空或子节点数突然为 0 的非叶子节点 | 增加 `depth` 参数重新获取 |
| 图片引用缺失 | fills 中 `type === 'IMAGE'` 但 `imageRef` 为空 | 标注为需手动补充的资源 |
| 文本节点无 `characters` | TEXT 节点缺少文本内容 | 使用节点 `name` 作为占位文本 |

## 四、预检后的处理决策树

```
对每个节点执行以下判断：

1. 是否为复合视觉效果节点？（2.1 条件 C1-C6）
   ├── 是 → 加入图片导出队列，在代码中使用 <img> 引用
   │         ⚠️ 禁止尝试 CSS 模拟
   │         ⚠️ 禁止在 CSS 模拟失败后再多次调整渐变参数
   └── 否 → 继续判断

2. 节点是否有简单渐变？（单层标准角度渐变）
   ├── 是 → 使用 CSS linear-gradient 还原
   └── 否 → 继续判断

3. 节点是否有纯色填充或纯图片？
   ├── 纯色 → CSS background-color
   ├── 纯图片（无 cropTransform）→ <img> 或 CSS background-image
   └── 其他 → 整体导出为图片（保守策略）
```

## 五、⚠️ 反模式警示（必须避免的错误操作）

以下是过往 D2C 实践中反复出现的**高频错误**，必须严格避免：

### 反模式 1：CSS 渐变反复试错

```
❌ 错误流程：
  1. 发现多层渐变 + 图片叠加
  2. 尝试用 CSS 多层 background 模拟 → 效果不对
  3. 调整渐变断点 → 效果更差
  4. 加更多渐变层 → 效果完全走样
  5. 多次沟通后才决定直接导出图片

✅ 正确流程：
  1. 预检发现多层渐变 + 图片叠加 → 判定为复合视觉效果节点
  2. 直接整体导出为图片 → 一步到位
```

### 反模式 2：层叠顺序错误导致元素被遮盖

```
❌ 错误：
  渐变遮罩在 DOM 中排在图片之后 → z-index 更高 → 图片被完全遮盖
  修复时手动加 z-index → 其他元素又被遮盖

✅ 正确：
  复合视觉效果直接导出为一张图，不存在层叠顺序问题
```

### 反模式 3：凭感觉调整渐变参数

```
❌ 错误：
  Figma 数据：73%→74% 硬断点
  AI 自行调整为 60%→80% → 效果不同
  AI 又调整为 50%→70% → 效果更不同
  每次调整都是基于猜测，无法收敛

✅ 正确：
  复合渐变效果不用 CSS 模拟，直接导出图片
  简单渐变严格按 Figma 数据的色标位置还原，禁止自由发挥
```

### 反模式 4：忽略 cropTransform

```
❌ 错误：
  Figma 图片有 cropTransform 裁剪矩阵
  用 CSS object-fit: cover + object-position 尝试模拟 → 无法精确还原
  
✅ 正确：
  检测到 cropTransform → 直接整体导出已裁剪的节点图片
```

## 七、背景图节点专项预检

> **此节针对 Banner、Hero、页面背景等大尺寸背景区域，确保在代码生成阶段不遗漏背景图资源。**

### 7.1 背景图节点识别

以下特征的节点应被识别为**背景图节点**：

| 特征 | 检测方法 | 说明 |
|------|---------|------|
| 节点名称含背景关键词 | `name` 包含 `banner`、`hero`、`bg`、`background`、`header-bg`（不区分大小写） | 命名暗示为背景用途 |
| 大尺寸 + IMAGE fill | 节点宽度 ≥ 800px 且 fills 包含 IMAGE 类型 | 大面积图片通常为背景 |
| 多层 fill 叠加（含 IMAGE） | fills 数组长度 ≥ 2，且至少 1 个 IMAGE + 至少 1 个 SOLID/GRADIENT | 复合背景效果 |
| 节点为 section/page 的第一层子节点且含 IMAGE | 位于页面顶部区域（y ≤ 页面高度的 30%），fills 含 IMAGE | 页面头部背景 |

### 7.2 背景图节点的处理决策

```
对每个识别出的背景图节点：

1. 检查 fills 数组：
   ├── 仅 1 个 IMAGE fill，无 cropTransform → 标记为"简单背景图"
   │   → 可使用 MCP 模式 C 导出，或 CSS background-image
   ├── IMAGE + 其他 fill 叠加 → 标记为"复合背景图"（命中 C7）
   │   → 必须使用 MCP 模式 C（节点渲染）整体导出
   └── IMAGE 含 cropTransform → 标记为"裁剪背景图"（命中 C2/C8）
       → 使用 MCP 模式 C 导出 + 导出后验证视觉完整性

2. 检查 clipContent：
   ├── clipContent === true + IMAGE 超出边界 → ⚠️ 高风险
   │   → 导出后必须验证，可能需要用户手动从 Figma 导出
   └── clipContent === false 或 IMAGE 未超出 → 正常处理

3. 输出背景图处理方案到预检报告
```

### 7.3 预检报告中的背景图专项

```
🖼️ 背景图节点（需特殊处理）
  序号 | 节点ID    | 节点名称         | 尺寸        | fill 类型            | 风险    | 处理策略
  1    | 495:190  | banner-bg      | 2560×400   | SOLID+IMAGE+GRAD+SOLID | ⚠️ 高  | 节点渲染导出 @2x + 导出后验证
  2    | 830:100  | hero-section   | 1440×600   | IMAGE                 | 低     | 节点渲染导出 @2x
```

### 7.4 与 Auto Layout 的布局关系确认

背景图节点通常是**容器背景**，其上方有文字、按钮等内容叠加。预检时必须同时确认：

1. **内容层子节点的完整性** — 确保背景容器内的所有子节点（标题、描述、按钮等）都被正确识别
2. **内容层的布局方向** — 确认 Auto Layout 方向（水平/垂直）和子元素排列关系
3. **同行元素的包裹关系** — 如果多个子元素在同一行水平排列（如"繼續學習"按钮和课程名称），确认它们是否在同一个水平 Auto Layout 容器中

```
⚠️ 常见布局偏差预警：
  - 嵌套的水平 Auto Layout 可能被扁平化 → 同行元素变成换行
  - 确保 Figma 中 layoutMode="HORIZONTAL" 的容器在代码中保持 flex-row
  - 确保同一父容器下的 itemSpacing 正确映射为 gap
```

## 八、坐标系统与自适应布局预判

> **此节在 Step 2.5 执行，确保在代码生成前完成坐标系统建立和自适应布局方案确定。**

### 8.1 坐标系统预判

**在预检阶段必须完成以下坐标分析（输出到预检报告中）：**

```
预判流程：

1. 读取根节点 boundingBox → 记录设计稿基准宽度（如 1920px）
2. 遍历根节点的直接子节点，提取每个的 (x, y, w, h)
3. 识别内容区域：
   - 找出最多子元素集中的 x 区间（如 370~1550）
   - 内容宽度 = 最大 x + w - 最小 x（如 1550 - 370 = 1180px）
   - 左边距 = 最小 x（如 370px）
   - 右边距 = 根宽度 - 最大 x - w（如 1920 - 1550 = 370px）
4. 判定居中：|左边距 - 右边距| ≤ 10px → 确认居中布局
5. 识别超宽区域：x < 0 或 x + w > 根宽度 的节点
6. 识别全宽区域：w ≈ 根宽度（±5%）的节点
```

### 8.2 自适应布局预判

```
基于坐标分析结果，预判每个区域的自适应策略：

1. 页面根容器：w-full min-h-screen（不使用固定宽度）
2. 全宽背景区域：w-full overflow-hidden
3. 居中内容区域：max-w-[{内容宽度}px] mx-auto w-full px-4
4. 超宽装饰：父容器 overflow-hidden + 内容 object-cover / background-size: cover
5. 固定尺寸小元素：保持原始固定值

⚠️ 预判的自适应策略必须在后续 Step 4.0 中正式确认，
   预检阶段只做初步分析和风险标注。
```

### 8.3 布局风险预警

在预检报告中标注以下风险：

| 风险类型 | 检测条件 | 影响 | 处理建议 |
|---------|---------|------|---------|
| 无 Auto Layout 的大区域 | FRAME 无 layoutMode 且子节点 > 5 个 | 需纯坐标推导，易出错 | 优先使用坐标分组→flex 布局 |
| 子元素坐标不规则 | 同级子元素既有水平排列又有垂直排列 | 难以用单一 flex 方向覆盖 | 按 y 坐标分组为"行"，每行 flex-row |
| 重叠/变体节点 | 多个子元素坐标几乎完全重叠 | 可能是设计稿中的状态变体 | 只取一个实现 |
| 固定宽度风险 | 设计稿内容区宽度 > 1400px | 小屏幕下可能溢出 | 必须使用 max-width + 居中 |

### 8.4 与其他预检项的关联

```
坐标系统预判 → 输入到 Step 4.0（坐标系统建立）
自适应预判 → 输入到 Step 7.5（自适应布局转换）
布局风险 → 输入到 Step 7.6（坐标-布局一致性验证）

如果预检发现布局风险较高（无 Auto Layout + 子节点多 + 坐标不规则），
应在预检报告中标注：
  ⚠️ 布局复杂度：高 — 建议优先基于坐标数据建立布局，不依赖 Auto Layout
```
