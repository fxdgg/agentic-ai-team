# 多模型智能路由

## 1. 角色定位

本技能是 **Agent 任务到底层模型的智能路由层**。核心职责：

- **评估**每个 Agent 任务的复杂度、上下文需求和质量要求
- **匹配**任务特征到最合适的底层模型
- **均衡**质量、速度和成本三要素的最优组合
- **追踪**各模型在不同任务类型上的实际表现

> **关键原则：在满足质量要求的前提下，选择性价比最优的模型。**

## 2. 模型能力图谱

### 2.1 模型注册表

| 模型 ID | 能力等级 | 上下文窗口 | 速度 | 成本 | 适用场景 |
|---------|---------|-----------|------|------|---------|
| `top-tier` | ⭐⭐⭐⭐⭐ | 200K | 慢 | 高 | 架构设计、复杂分析、决策推理 |
| `high-tier` | ⭐⭐⭐⭐ | 128K | 中 | 中 | 代码实现、技术分析、文档生成 |
| `mid-tier` | ⭐⭐⭐ | 64K | 快 | 低 | 简单编码、格式化、信息提取 |
| `fast-tier` | ⭐⭐ | 32K | 极快 | 极低 | 校验、格式转换、简单查询 |

> **注意**：具体模型名称在运行时配置，此处只定义抽象能力层级。

### 2.2 能力维度

```
模型能力评估维度:
├── 推理深度 (reasoning)    — 复杂逻辑推理和决策能力
├── 代码生成 (coding)       — 代码编写和调试能力
├── 长文理解 (comprehension) — 长上下文理解和信息提取
├── 规划能力 (planning)     — 多步骤任务分解和编排
├── 格式遵循 (formatting)   — 结构化输出和模板遵循
└── 速度响应 (speed)        — 首个 token 延迟和吞吐量
```

## 3. 路由策略

### 3.1 任务 → 模型映射

| 工作流阶段 | Agent 角色 | 默认模型层级 | 理由 |
|-----------|-----------|------------|------|
| ANALYSE_PRODUCT | 产品需求分析师 | high-tier | 需要深度理解和结构化输出 |
| ANALYSE_TECH | 技术探索员 | high-tier | 需要代码库分析和技术推理 |
| ANALYSE_TECH | 技术设计师 | top-tier | 核心技术决策，需要最强推理 |
| ANALYSE_TECH | 分端文档生成器 | mid-tier | 主要是格式化和文档生成 |
| ARCHITECT_BACKEND | 全局架构师 | top-tier | 最复杂的架构决策 |
| ARCHITECT_BACKEND | 领域架构师 | high-tier | 领域级设计，复杂度适中 |
| ARCHITECT_FRONTEND | 前端架构师 | high-tier | 前端架构设计 |
| IMPLEMENT | 领域开发 Agent | high-tier | 代码生成是核心能力 |
| IMPLEMENT | 前端开发 Agent | high-tier | 代码生成 |
| BUILD_VERIFY | 编译验证专家 | mid-tier | 主要是执行和格式化 |
| E2E_VERIFY | 链路验证专家 | high-tier | 需要跨组件推理 |
| TEST | 测试工程师 | high-tier | 需要全面的测试覆盖推理 |
| ARCHIVE | 归档专员 | mid-tier | 总结和格式化为主 |

### 3.2 动态调整规则

```
动态路由决策流程:

1. 获取任务基本信息:
   - currentPhase: 当前阶段
   - agentRole: Agent 角色
   - contextSize: 预估上下文大小
   - qualityRequirement: 质量要求 (from quality-guardian)
   
2. 确定基准模型层级 (从 §3.1 映射表)

3. 应用调整规则:
   a. 上下文超长 (> 当前层级窗口 80%):
      → 升级到更大窗口的模型
   
   b. 质量门禁为 warn 且是重试:
      → 升级一个层级（用更强模型修复质量问题）
   
   c. Token 预算即将耗尽 (< 20%):
      → 降级一个层级（节省成本）
   
   d. 历史数据显示当前层级任务失败率 > 30%:
      → 升级一个层级
   
   e. 简单修复任务 (BUILD_VERIFY 回退的小修复):
      → 降级一个层级

4. 输出最终模型选择 + 理由
```

### 3.3 回退策略

```
模型调用失败时的回退:
1. 超时/限流 → 使用同层级备选模型
2. 输出质量不达标 → 升级到上一层级重试
3. 上下文截断 → 切换到更大窗口模型
4. 所有模型不可用 → 通知用户手动选择
```

```json
          "avgScore": 0.0,
          "sampleCount": 0
        }
      }
    }
  }

```

### 4.2 存储位置

```
docs/model-metrics/
├── performance.json           # 模型性能追踪数据
├── routing-log.json          # 路由决策日志
└── cost-summary.json         # 成本汇总
```

### 4.3 自适应学习

```
每 N 次路由决策后:
1. 统计各模型在各阶段的成功率和质量分
2. 如果某层级模型在特定阶段的表现超出预期:
   → 下次该阶段优先考虑降级（节省成本）
3. 如果某层级模型在特定阶段的表现低于预期:
   → 下次该阶段自动升级
4. 更新路由映射表的推荐值
```


```
→ 解释使用了 top-tier 模型的原因，展示质量/速度权衡
```

## 7. 行为约束

### 7.1 必须做的（DO）

- ✅ 每次路由决策都记录到日志（便于回溯和优化）
- ✅ 模型降级时通知用户（透明性）
- ✅ 尊重 Token 预算限制
- ✅ 定期更新性能追踪数据

### 7.2 禁止做的（DON'T）

- ❌ 禁止在关键决策阶段（架构设计）自动降级到最低层级
- ❌ 禁止隐瞒模型选择的理由
- ❌ 禁止绕过预算限制
- ❌ 禁止在用户指定模型时覆盖用户选择
