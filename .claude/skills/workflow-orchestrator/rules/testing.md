# 测试验证规则

> **状态**: 已完成
> **适用 Agent**: 测试验证专家（test-engineer）
> **适用阶段**: TEST

---

## 1. 核心原则

### 1.1 验证哲学

> **"基于代码事实，而非假设推演"**

- 所有验证结论必须**可溯源到具体的源码文件和代码行**
- 禁止"应该没问题"、"一般不会出错"等主观判断
- 当无法从代码中确定结论时，标记为 ⚠️ WARN 并说明不确定原因

### 1.2 验证铁律

| 规则 ID | 铁律 | 说明 |
|---------|------|------|
| **TR-01** | 只读不改 | 测试验证专家**严禁修改任何源码**，仅输出测试方案和报告 |
| **TR-02** | 证据先行 | 每个 FAIL/WARN 判定必须附带具体的代码引用（文件路径 + 方法名） |
| **TR-03** | 不重复验证 | E2E 链路验证 Agent 已覆盖的维度（上下文传播、事务边界等）不再重复，直接继承结论 |
| **TR-04** | 场景驱动 | L2 推演必须从**用户操作场景**出发，不做脱离场景的孤立代码审查 |
| **TR-05** | 分层清晰 | L1/L2/L3 三层验证严格分离，不混淆自动验证和人工验证的边界 |
| **TR-06** | 优先级明确 | 先验证 P0 核心路径，再覆盖 P1/P2 场景，不做无优先级的全面扫描 |

## 2. L1 接口契约验证规范

### 2.1 契约来源优先级

当前端调用签名与后端实现不一致时，**以技术需求总纲中的接口基准契约为裁判标准**：

```
技术需求总纲（analysis/tech-requirements.md §3.2 接口签名详情）
    ↓ 最高优先级：定义了"应该是什么"
前端实现（api.ts + types.ts）
    ↓ 对照源 A：前端"实际调了什么"
后端实现（Controller + DTO/VO）
    ↓ 对照源 B：后端"实际接了什么"
```

- 若前端偏离总纲 → 前端问题
- 若后端偏离总纲 → 后端问题
- 若两端都偏离总纲 → 双端问题（严重度升级）
- 若两端一致但都偏离总纲 → ⚠️ WARN（可能是总纲更新后未同步）

### 2.2 路径匹配规则

考虑前端代理配置（如 Vite proxy）对路径的影响：

```
前端请求路径          代理规则            后端接收路径
/api/admin/auth/login  →  proxy /api → target:9102  →  /api/admin/auth/login
```

验证时需要：
1. 读取前端构建工具的代理配置（如 `vite.config.ts` 中的 `proxy`）
2. 计算经过代理转换后的实际路径
3. 将转换后的路径与后端 Controller 的 `@RequestMapping` 进行匹配

### 2.3 类型映射规则

前后端类型对照表（常见映射）：

| TypeScript 类型 | Java 类型 | 判定 |
|----------------|-----------|------|
| `number` | `int` / `Integer` / `long` / `Long` | ✅ PASS（注意 JS number 精度限制：超过 2^53 的 Long 需用 string） |
| `string` | `String` | ✅ PASS |
| `boolean` | `boolean` / `Boolean` | ✅ PASS |
| `string` | `LocalDateTime` / `LocalDate` | ✅ PASS（JSON 序列化为 string） |
| `number` | `BigDecimal` | ⚠️ WARN（精度丢失风险） |
| `string` | `Long` | ✅ PASS（大数安全策略） |
| `number[]` | `List<Integer>` | ✅ PASS |
| `object` | Java 对象 | 需递归比对字段 |

### 2.4 字段必填性规则

| 前端 | 后端 | 判定 |
|------|------|------|
| 必填字段 | 有 `@NotNull` / `@NotBlank` | ✅ PASS |
| 必填字段 | 无校验注解 | ⚠️ WARN（后端未做校验） |
| 可选字段 | 有 `@NotNull` | ⚠️ WARN（前端可能不传导致后端 400） |
| 可选字段（`?`） | 无校验注解 | ✅ PASS |

## 3. L2 业务场景推演规范

### 3.1 场景编写标准

每个场景必须包含：
- **明确的起点**: 用户在哪个端执行什么操作
- **完整的调用链**: 从 UI 事件 → 前端逻辑 → API 请求 → 后端处理 → DB 操作 → 响应回传
- **关键断言点**: 在调用链的每个关键节点标注预期数据状态
- **异常分支**: 至少覆盖 2 个关键异常路径

### 3.2 推演深度要求

| 场景类型 | 追踪深度 | 说明 |
|---------|---------|------|
| 单接口场景 | 前端 hooks → api → 后端 Controller → Service → Mapper | 完整链路 |
| 跨端场景 | 端 A 完整链路 + 端 B 读取/展示逻辑 | 需验证数据一致性 |
| 跨服务场景 | 发起方 Service → Feign Client → 接收方 Controller → Service | 需验证参数传递 |
| 异步场景 | 发起方 → MQ Producer → Consumer → Service → DB | 需验证消息格式 |

### 3.3 高风险模式识别

以下代码模式在推演中应重点关注：

| 模式 | 风险 | 检查方法 |
|------|------|---------|
| 前端硬编码的枚举值 | 前后端枚举不同步 | 比对前端常量与后端 enum |
| 后端返回 null 的字段 | 前端未做空值处理 | 追踪 VO 字段的 null 可能性 → 前端是否有 `?.` 或默认值 |
| 错误码分支 | 前端未处理某些错误码 | 列出后端所有可能的 ResultCode → 检查前端响应拦截器覆盖度 |
| 分页参数 | pageNo 从 0 还是 1 开始 | 比对前后端的分页约定 |
| 时间格式 | 序列化/反序列化格式不一致 | 检查 `@JsonFormat` 和前端解析逻辑 |
| Token 生命周期 | 过期/续期/登出的完整处理 | 追踪 Token 生成 → 存储 → 携带 → 验证 → 续期 → 清除的完整链路 |

### 3.4 继承 E2E 验证上下文

测试验证专家在 L2 推演时，必须读取 E2E 链路验证的结果（追加在 `implementation/backend/*-report.md` 末尾的「端到端链路验证」章节）：

- **PASS 项**: 不再重复验证，直接引用
- **WARN 项**: 在 L2 推演中额外关注该场景路径，尝试通过业务场景推演确认是否真的有问题
- **FAIL 项**: 在测试报告中标注为已知问题，评估对业务场景的影响

## 4. L3 人工测试用例规范

### 4.1 用例设计原则

- **可执行性**: 每个用例必须包含具体的操作步骤和预期结果，任何测试人员都能按步骤执行
- **可判定性**: 预期结果必须是明确可判定的（"页面显示手机号 138****8000"而非"页面正常显示"）
- **独立性**: 每个用例可独立执行，不依赖其他用例的执行结果
- **可追溯性**: 每个用例关联到具体的业务场景或风险项

### 4.2 优先级分配规则

| 优先级 | 定义 | 占比建议 |
|--------|------|---------|
| **P0** | 核心验收标准、涉及资金安全、用户认证的场景 | 20-30% |
| **P1** | 关键异常流、跨端联调点、已知风险项关联场景 | 30-40% |
| **P2** | 边界场景、兼容性、性能、非核心路径 | 30-40% |

### 4.3 跨端联调用例规范

涉及多端协作的用例必须：
- 明确标注**端切换节点**（如"在 Web 端完成审核后，切换到小程序端验证"）
- 标注**数据同步等待时间**（如"等待 MQ 消费完成，预计 3-5 秒"）
- 提供**验证数据的查询方式**（如"通过 Redis CLI 查询 key `sms:code:{phone}` 确认验证码"）

## 5. 覆盖率要求

### 5.1 L1 覆盖率

| 指标 | 要求 |
|------|------|
| 接口覆盖率 | 本次变更涉及的所有接口必须 100% 覆盖 |
| 字段覆盖率 | 请求体和响应体的所有字段必须逐一比对 |
| 路径参数/查询参数 | 必须 100% 覆盖 |

### 5.2 L2 覆盖率

| 指标 | 要求 |
|------|------|
| PRD 验收标准 | 100% 覆盖（每个验收标准至少对应一个推演场景） |
| 核心正常流 | 100% 覆盖 |
| 关键异常流 | 每个接口至少 2 个异常场景 |
| 跨端场景 | 启用 ≥2 端时，100% 覆盖跨端交互点 |

### 5.3 L3 覆盖率

| 指标 | 要求 |
|------|------|
| P0 用例 | 必须覆盖所有核心验收标准 |
| UI 验证 | 每个新增/修改页面至少 1 个 UI 验证用例 |
| 安全验证 | 涉及认证/授权的需求必须包含安全用例 |
| 兼容性 | 按需（仅涉及 CSS/响应式变更时） |

## 6. 报告质量标准

### 6.1 测试方案（test-plan.md）

- [ ] 包含完整的 YAML front-matter
- [ ] 场景覆盖矩阵覆盖所有 PRD 验收标准
- [ ] 明确标注各验证层的适用端和预计验证项数
- [ ] 前置依赖清单可操作

### 6.2 测试报告（test-report.md）

- [ ] L1 验证逐接口逐字段列出结果
- [ ] L2 推演逐步骤标注代码溯源
- [ ] L3 用例符合模板规范
- [ ] 问题清单按严重度排序
- [ ] 质量评分计算过程透明

### 6.3 问题描述规范

每个问题必须包含：

```markdown
| 字段 | 要求 |
|------|------|
| 问题描述 | 一句话说明问题本质 |
| 代码位置 | 前端: `{文件}::{行/方法}` + 后端: `{文件}::{行/方法}` |
| 预期行为 | 按 PRD/总纲，应该是什么 |
| 实际行为 | 从代码中读到的实际实现 |
| 影响范围 | 影响哪些场景/用户操作 |
| 修复建议 | 具体的修复方向（标注应该由哪个 Agent 修复） |
```

## 7. 与编排器的交互约定

### 7.1 产物路径

| 产物 | 相对路径（基于需求目录） |
|------|----------------------|
| 测试方案 | `testing/test-plan.md` |
| 测试报告 | `testing/test-report.md` |

### 7.2 回退时的清理范围

当 TEST 阶段回退时，编排器删除：
- `testing/test-plan.md`
- `testing/test-report.md`

### 7.3 断点恢复

TEST 阶段支持断点恢复。恢复时：
1. 检查 `testing/` 目录是否已有产物
2. 若有 → 读取已有产物，询问用户是否重新生成
3. 若无 → 从头开始执行
