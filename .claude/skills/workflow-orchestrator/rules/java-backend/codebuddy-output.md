# Claude Code 输出约束与默认开发原则

> 本规则覆盖：代码生成约束、输出规范、默认开发原则。

## 1. 代码生成通用约束
- 生成代码时必须严格遵守微服务开发契约。
- 若需求与契约冲突，**优先指出冲突点**，不得擅自忽略。
- 生成 Controller / Service / Mapper / DTO / VO / Entity / Convert / Feign Client 代码时，必须遵守分层规范。
- 生成数据库操作代码时，必须默认考虑多租户隔离。
- 生成接口代码时，返回值必须为 `Result<T>`。
- 生成查询代码时，必须优先使用 MyBatis Plus 的 Lambda 风格写法。
- 生成微服务调用代码时，必须优先使用 Nacos + Feign。

## 2. 配置生成约束
- 生成配置相关代码或说明时，必须明确区分：
  - 本地启动配置
  - 本地环境配置
  - Nacos 共享配置
  - Nacos 服务配置
  - Nacos 租户配置
- 生成 `yml` 示例时，不得将所有配置堆叠在一个文件中。
- 生成 Nacos 配置方案时，必须说明 `DataId`、`Group`、`Namespace` 的使用方式。
- 生成租户配置方案时，必须遵守 `{tenantId}.{configName}` 命名规范。

## 3. Package 生成约束
- 生成代码时，必须同时给出合理 package 声明。
- 生成的 package 必须与模块职责一致，不得出现职责错位。
- **CRITICAL**: 本项目**强制采用「扁平式分包 + 技术层内业务域子包」**风格，具体规则见 `package-structure.md` §5。
- **CRITICAL**: 根包下**只允许**出现技术层包（`controller`、`service`、`mapper`、`entity`、`convert`、`client`、`config`、`exception`、`enums`、`constant` 等），**严禁**在根包下创建业务域包（如 `menu/`、`tenant/`、`order/`）。
- **CRITICAL**: 业务域的划分在技术层包内部完成。例如菜单相关的 Mapper 放在 `mapper/menu/SysMenuMapper.java`，而非 `menu/mapper/SysMenuMapper.java`。
- **CRITICAL**: 无论业务域下当前文件数量多少，都必须按业务域分子包，保持规则一致性。
- 生成新类时，应优先放入已有语义明确的 package，而不是随意新建模糊 package。
- 若用户未提供根包名，可先采用占位格式：`com.xxx.{business}.{service}`

## 4. Entity 与表结构生成约束
- 生成 Entity 时，必须包含通用审计字段定义，除非用户明确说明已有基类承载。
- 生成表结构建议时，必须默认包含：`id`、`tenant_id`、`created_by`、`created_time`、`updated_by`、`updated_time`、`deleted`。
- 生成新增/更新代码时，默认依赖自动填充机制，不得手工在每个方法中重复写审计字段赋值逻辑。
- 生成唯一索引建议时，必须默认检查是否需要带上 `tenant_id`。
- 生成金额字段时，不得使用 `double`。
- 生成逻辑删除代码时，必须遵守 `deleted: 0/1` 统一规则。

## 5. 分页与查询生成约束
- 生成列表查询接口时，必须默认提供分页能力，除非用户明确说明为详情、下拉选项、少量枚举数据。
- 生成查询 DTO 时，必须包含清晰的分页字段与查询字段。
- 生成分页返回时，默认使用 `Result<PageResult<VO>>`。
- 生成排序逻辑时，必须使用白名单控制，不得直接拼接前端排序参数。
- 生成 Mapper/Service 查询代码时，必须优先使用 MyBatis Plus 分页与 Lambda 条件构造。
- 生成导出方案时，不得简单复用普通分页查询并放大页大小。

## 6. DDL 与代码生成顺序约束
- **CRITICAL**: 若需求涉及数据库结构变更或代码实现依赖底层表结构，必须先检查并同步当前域服务 `sql` 目录下的 DDL 文件，确认库表结构一致后，方可生成或修改业务代码。
- 生成任何涉及数据库结构的代码前，必须优先参考服务内 `sql` 目录中的 DDL。
- 若任务会改动底层数据结构，必须先输出或更新对应 DDL，再继续输出业务代码。
- 若未提供 DDL 文件，但需求明显依赖表结构，必须先提示缺少 DDL 依据，不得臆造数据库结构后直接生成完整持久层代码。
- 生成 Entity、Mapper、查询逻辑时，必须以 DDL 为准，而不是仅根据字段字面猜测。
- 若发现 DDL 与现有代码冲突，必须显式列出冲突项（字段缺失、类型不一致、主键策略不一致、审计字段不一致、逻辑删除字段不一致、多租户字段缺失）。
- 生成 SQL 脚本时，默认放置于当前域服务的 `sql/ddl` 目录下。
- 除非用户明确要求，否则不得跳过"先审视 DDL，再改业务代码"的流程。

## 7. 其他约束
- 除非明确要求，否则不要生成冗余 XML、工具类或与当前需求无关的代码。

---

## 8. 默认开发原则
- 优先保证 **正确性**，再考虑 **性能** 与 **优雅性**。
- 优先保证 **租户隔离** 与 **安全性**。
- 优先输出 **可维护**、**可读**、**符合团队规范** 的代码。
- 对不明确需求，先做最小合理假设，并显式说明。
- 对跨服务调用，优先保证 **稳定性**、**可观测性** 与 **边界清晰**。
- **数据库结构是业务代码生成的前置依据，DDL 先于 Entity，Entity 先于 Mapper，Mapper 先于 Service。**
