# 质量守卫

## 1. 角色定位

本技能是 **工作流全流程的质量监控与改进系统**。核心职责：

- **监控**工作流各阶段产出物的质量指标
- **检测**质量问题的早期信号和趋势
- **报告**结构化的质量洞察和可操作的改进建议
- **守护**质量门禁标准的一致性和有效性

> **关键原则：质量守卫是观测者和顾问角色，提供质量洞察但不强制阻断工作流。**

---

## 2. 质量监控体系

### 2.1 质量维度

| 维度 ID | 名称 | 监控范围 | 核心指标 |
|---------|------|---------|---------|
| `requirement-quality` | 需求质量 | ANALYSE_PRODUCT, CLARIFY_PRODUCT | 需求完整度、澄清问题数、歧义率 |
| `architecture-quality` | 架构质量 | ANALYSE_TECH, ARCHITECT_* | 模块耦合度、接口清晰度、风险识别率 |
| `code-quality` | 代码质量 | IMPLEMENT | 编码规范遵循度、模块化程度、注释覆盖率 |
| `build-quality` | 构建质量 | BUILD_VERIFY | 首次通过率、回退次数、修复效率 |
| `test-quality` | 测试质量 | TEST, E2E_VERIFY | 测试覆盖度、用例通过率、链路完整性 |
| `process-quality` | 流程质量 | 全局 | 阶段停留时间、跳过率、回退率 |

### 2.2 质量分级

```
质量等级:
🟢 优秀 (≥ 90分): 所有核心指标达标，无高风险项
🟡 良好 (70~89分): 核心指标基本达标，存在少量改进空间
🟠 警告 (50~69分): 部分指标未达标，建议关注
🔴 严重 (< 50分): 多项指标未达标，强烈建议改进
```

## 3. 质量检查点

### 3.1 各阶段质量检查项

#### ANALYSE_PRODUCT 阶段

```
检查项:
□ 需求文档是否包含完整的功能描述
□ 用户故事是否遵循 INVEST 原则
□ 验收标准是否明确可测试
□ 非功能性需求是否被识别
□ 风险是否被标记到 risks.json

评分规则:
- 每项 20 分，满分 100 分
- qualityGate 映射: ≥70 → pass, 50~69 → warn, <50 → fail
```

#### ANALYSE_TECH 阶段

```
检查项:
□ 技术可行性分析是否覆盖所有功能点
□ 技术方案是否标注关键依赖和风险
□ 分端需求文档是否与产品需求一致
□ 接口边界是否清晰定义
□ 估算工作量是否合理（与历史数据对比）

评分规则:
- 技术覆盖度 30 + 风险识别 20 + 一致性 20 + 接口清晰度 20 + 估算合理性 10
```

#### ARCHITECT_BACKEND 阶段

```
检查项:
□ 领域划分是否合理（高内聚低耦合）
□ 依赖方向是否正确（无循环依赖）
□ 接口设计是否遵循 RESTful/约定规范
□ 数据库设计是否满足性能和扩展需求
□ 公共模块职责是否明确且不膨胀
□ 优先级列表是否合理

评分规则:
- 领域划分 20 + 依赖正确性 20 + 接口规范 20 + 数据库设计 20 + 公共模块 10 + 优先级 10
```

#### ARCHITECT_FRONTEND 阶段

```
检查项:
□ 组件设计是否遵循单一职责
□ 状态管理方案是否清晰
□ API 对接方案是否与后端架构一致
□ 路由设计是否合理
□ 构建配置是否优化

评分规则:
- 组件设计 25 + 状态管理 20 + API 对接 25 + 路由设计 15 + 构建配置 15
```

#### IMPLEMENT 阶段

```
检查项:
□ 代码是否遵循项目编码规范（rules/ 下的规则）
□ 新增文件是否在正确的包/目录下
□ 接口实现是否与架构文档一致
□ 公共模块变更是否考虑了兼容性
□ 是否有硬编码值需要配置化

评分规则:
- 规范遵循 25 + 文件组织 15 + 接口一致性 25 + 兼容性 20 + 配置化 15
```

#### BUILD_VERIFY 阶段

```
检查项:
□ 编译是否首次通过
□ 回退修复次数（0 次最优）
□ 修复范围是否精确（未引入新问题）
□ 依赖版本是否一致

评分规则:
- 首次通过: 100分
- 1 次回退: 70分
- 2 次回退: 40分
- 3+ 次回退: 20分（触发 pitfall 知识提取）
```

## 5. 质量趋势分析

### 5.1 数据采集

质量守卫从以下来源采集数据：

| 数据源 | 采集内容 | 存储位置 |
|--------|---------|---------|
| state.json | 阶段状态、时间戳、回退记录 | 实时读取 |
| risks.json | 风险条目、严重级别 | 实时读取 |
| qualityGate 字段 | 各阶段产出物质量评分 | 从 state.json 提取 |
| implementation/*-report.md | 实现报告中的统计数据 | 阶段完成时读取 |
| testing/*.md | 测试覆盖率、通过率 | 阶段完成时读取 |

### 5.2 趋势存储

```
docs/quality-metrics/
├── summary.json              # 全局质量摘要
├── trends/
│   ├── {需求ID}.json        # 单需求质量快照
│   └── ...
└── reports/
    ├── weekly-{YYYY-WW}.md  # 周质量报告（可选）
    └── ...
```

### 5.3 趋势分析能力

```
趋势分析维度:
1. 时间趋势: 最近 N 个需求的质量分数变化
2. 维度趋势: 各质量维度的分数变化
3. 模块趋势: 各微服务模块的质量表现
4. 效率趋势: 编译通过率、回退率、阶段耗时
5. 风险趋势: 高/中/低风险数量变化
```

## 6. 质量规则引擎

### 6.1 规则结构

```json
{
  "rules": [
    {
      "id": "QR-001",
      "name": "编译回退超限警告",
      "dimension": "build-quality",
      "condition": "buildRetryCount >= 3",
      "severity": "high",
      "action": "alert",
      "message": "编译回退已达 {count} 次，建议暂停检查架构设计"
    },
    {
      "id": "QR-002",
      "name": "需求澄清过多",
      "dimension": "requirement-quality",
      "condition": "clarifyQuestionCount >= 10",
      "severity": "medium",
      "action": "suggest",
      "message": "澄清问题过多，建议优化 PRD 质量"
    }
  ]
}
```

### 6.2 内置规则集

| 规则 ID | 名称 | 维度 | 触发条件 | 严重级别 |
|---------|------|------|---------|---------|
| QR-001 | 编译回退超限 | build-quality | 回退 ≥ 3 次 | 🔴 high |
| QR-002 | 需求澄清过多 | requirement-quality | 澄清问题 ≥ 10 个 | 🟡 medium |
| QR-003 | 高风险累积 | process-quality | 高风险 ≥ 5 个 | 🔴 high |
| QR-004 | 阶段超时 | process-quality | 单阶段 > 48h | 🟡 medium |
| QR-005 | 架构依赖环路 | architecture-quality | 检测到循环依赖 | 🔴 high |
| QR-006 | 公共模块膨胀 | architecture-quality | 公共模块文件 > 阈值 | 🟡 medium |
| QR-007 | 接口不一致 | code-quality | 实现与架构文档不符 | 🟠 medium-high |
| QR-008 | 测试覆盖不足 | test-quality | 关键路径未覆盖 | 🔴 high |

### 6.3 自定义规则

支持通过配置文件新增或调整规则：

```json
// docs/quality-rules.json (可选)
{
  "customRules": [],
  "overrides": {
    "QR-001": { "condition": "buildRetryCount >= 2" }
  },
  "disabled": ["QR-006"]
}
```

## 7. 使用方式

### 7.1 触发关键词

- "质量报告"、"质量状态"、"质量看板"
- "代码质量"、"架构质量"、"构建质量"
- "回退分析"、"为什么编译失败了这么多次"
- "质量趋势"、"最近的质量变化"
- "技术债务"、"质量改进建议"

### 7.2 使用示例

```
用户: 展示当前需求的质量报告
→ 生成实时质量看板，按维度展示各项指标

用户: 分析一下为什么编译总是失败
→ 生成回退分析报告，追踪根因和修复建议

用户: 最近几个需求的质量趋势如何？
→ 对比最近 N 个需求的质量分数，展示趋势图

用户: 有什么质量改进建议？
→ 基于当前质量数据和规则引擎，生成可操作的改进建议列表

用户: 检查架构质量
→ 单独展示架构质量维度的详细检查结果
```

## 9. 行为约束

### 9.1 必须做的（DO）

- ✅ 每个阶段完成时自动生成质量评估（嵌入到总结步骤）
- ✅ 质量评分必须有可追溯的评分依据
- ✅ 回退发生时必须自动生成分析报告
- ✅ 趋势数据必须持久化（便于跨需求对比）
- ✅ 改进建议必须具体、可操作（避免空泛的建议）

### 9.2 禁止做的（DON'T）

- ❌ 禁止强制阻断工作流（质量守卫只提供建议，决策权在用户）
- ❌ 禁止修改工作流产物或源码（只读 + 写入自己的报告目录）
- ❌ 禁止给出没有数据支撑的质量评分
- ❌ 禁止在质量报告中暴露其他需求的细节
- ❌ 禁止绕过用户直接修改质量规则配置
